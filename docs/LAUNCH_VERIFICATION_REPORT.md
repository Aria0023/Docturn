## 1. Verdict

**No-go.** The server core is genuinely solid — tenant isolation, RBAC, MFA mechanics, session expiry, rate limiting, messaging delivery, the routing algorithm and the honesty of the compliance monitor all held under adversarial probing — but seven launch blockers stand between this commit and a hospital. Four were confirmed by independent skeptic re-verification: the sign-in form discards whatever the user types and always posts the demo account `chen`/`docturn`, so no real user can sign in from the UI and on a real-PHI deployment nobody can; every clinician a director provisions gets the public demo password with no forced change; MFA shows "Off" to enrolled users and one click re-enrols without a password, destroying the live authenticator, with no disable or reset route; patient purge hangs on a foreign-key violation, silently deletes assignments/consults, and takes the hourly auto-clean down with it. Two were established by the completeness critic: there is no way to terminate a clinician's access, and the runbook's own real-PHI bootstrap yields a director account with an unknowable password. One was reported by the messaging probe and carried by the critic as open, but its skeptic record did not reach this report: forwarded attachments return 27 bytes of garbage under the production `fs-encrypted` store. The critic's recommendation is no-go; the confirmed blockers agree with it, so there is nothing to reconcile. None of the fixes is large and "go-with-fixes" is reachable in one focused sprint. **Fix list:** send the typed org/username/password from `webapp/LoginScreen.jsx:92` through `webapp/index.html:327` into `doLogin` (`webapp/api-bridge.js:645-693`) and delete every hardcoded `"docturn"` (`api-bridge.js:122, 673, 1614, 1652`); have `POST /api/director/hospitalists` mint a server-side one-time password and enforce a must-change flag; make `POST /api/mfa/enroll` require password + current code when MFA is on, keep the active secret until `/api/mfa/verify`, add disable/regenerate/admin-reset and return `twoFactorEnabled`; wrap `purgeOldPatients` in a transaction that clears `conversations.patient_id` and move auto-clean's try/catch inside the per-org loop; add `users.active` with a director deactivate route enforced in `deserializeUser` and the WebSocket upgrade; make `POST /api/dev/users` return or accept an initial password and add a reset route; resolve `fsenc:` refs through the attachment store in the forwarded-attachment route.

## 3. Launch blockers

### LB-1 — Sign-in form discards typed credentials; always posts the demo account

**What happens.** Whatever a user types into Organization / Username / Password, the web app and the installed PWA send `{"orgCode":"ISPN","username":"chen","password":"docturn"}` (the selected role's demo account). In synthetic mode a wrong password signs you in, typing `patel` lands you as `chen`, and a user who changes their password in Account Settings locks themselves out of the UI. On a `SYNTHETIC_DATA=false` deployment there are no demo accounts, so every UI sign-in fails with "Sign-in failed: Wrong account/password for this role." — including the operator holding the correct `PLATFORM_ADMIN_PASSWORD`. The 401 self-heal and the role switcher re-login the same way, so a lost server session is silently replaced by the demo account. The Password field is security theatre.

**Evidence.** `webapp/api-bridge.js:646` `var username = DEMO[role] || user || "chen";` — `DEMO` (`:35-41`) has an entry for every role in the picker, so the typed `user` is dead code; `:647` `orgForRole()` rewrites DOCTURN → ISPN for non-developer roles; `:673` `rawApi("POST", "/api/login", { orgCode, username, password: "docturn" })`; `:120-123` the 401 self-heal re-posts the same body; `:751-765` role switch does too. `webapp/LoginScreen.jsx:92` `onLogin(role, org, user)` never passes `pass` (whose initial value is the literal `"••••••••"`, `:13`); `webapp/index.html:327` forwards `a.login(r, org, user)`. Observed in Chromium (iPhone UA, 390×844, 375×667 and 430×932) against the built server: typed `persist.probe`/`Probe12345` → request body `chen`/`docturn` → 200 as chen; typed `chen` + `definitely-wrong` → 200; typed `patel` → signed in as chen. Against a `SYNTHETIC_DATA=false` instance with `PLATFORM_ADMIN_PASSWORD` set: typed `DOCTURN`/`dev`/correct secret → body `ISPN`/`chen`/`docturn` → 401; the same credentials via direct `POST /api/login` → 200. The server-side `/api/login` is correct in every case; the defect is entirely in the client.

**Repro.** Open `/` on a phone, enter org `ISPN`, user `chen`, password `definitely-wrong`, tap Sign in → signed in; DevTools shows the POST body above. Real-PHI: `PORT=4105 PGLITE_DIR=/tmp/x SYNTHETIC_DATA=false PLATFORM_ADMIN_PASSWORD=Str0ng-Platform-Secret-2026 npx tsx server/index.ts`, then sign in as `DOCTURN`/`dev`/that secret → "Sign-in failed"; `curl -d '{"orgCode":"DOCTURN","username":"dev","password":"Str0ng-Platform-Secret-2026"}' -H 'Content-Type: application/json' http://127.0.0.1:4105/api/login` → 200.

**Fix.** (1) `webapp/LoginScreen.jsx:92` → `onLogin(role, org, user, pass)`; initialise `pass` to `""` at `:13` and use a placeholder. (2) `webapp/index.html:327` → `a.login(r, org, user, pass)`. (3) `webapp/api-bridge.js:645-693` `doLogin(role, org, user, pass)` posts exactly `{ orgCode: org.trim(), username: user.trim(), password: pass }`; delete `DEMO[role] || user || "chen"`, the `orgForRole()` rewrite and the canonical-org retry (`:48-51`, `:687-692`) from the credential path; derive the session role from the `/api/user` response (`finish()` already does). (4) Keep the role picker (`LoginScreen.jsx:68-84`) strictly as a prefill shown only when `syntheticData === true`. (5) `api-bridge.js:120-123` and `:751-765`: never re-authenticate with a hardcoded password — on a 401 for an established session clear `session` and show the LockScreen (`LockScreen.jsx:30-35` already posts the real password) or the login screen; gate role switching behind `syntheticData === true`. (6) Add browser tests: typed body equals posted body; wrong password → no session; `patel` lands as `patel`; on `SYNTHETIC_DATA=false` both `dev` and a director-created clinician can sign in from the UI; `/api/user` never returns a different user than the store's `session.user`.

**Verification.** Found independently by the baseline and auth probes. 4 skeptic re-verifications, 4 of 4 confirmed at high confidence, all rated launch-blocker, each on its own servers across three viewports and three server configurations (synthetic, synthetic + `DEMO_PASSWORD`, real-PHI).

### LB-2 — Every director-provisioned account gets the public demo password `docturn`, no forced change — also in real-PHI mode

**What happens.** The Add-provider modal (all roles, including director and ER roles) and the Amion import create accounts with password `docturn` and no must-change flag. The demo password is public (README, `api-bridge` comments, LoginScreen hint "any password") and usernames follow a predictable pattern (lowercased name with dots). Anyone who knows a clinician's name can log in as them and read patients. Unconditional — no `syntheticData` check — so it applies to a real-PHI deployment.

**Evidence.** `webapp/api-bridge.js:1614` `var body = { username: uname, password: "docturn", displayName: name, role: role };` (`addProvider` → `POST /api/director/hospitalists`); `:1652` same in `importProviders`; `:1613` username derivation. `server/routes/providers.ts:11` `password: z.string().min(6)` accepts it; `:131` hashes it. No must-change flag exists anywhere (`rg mustChange|forcePasswordChange|tempPassword` → only `server/routes/dev.ts:380`, the developer route's discarded random hash). Observed: POST with the exact client body → `201 {user:{id:30}}`; `POST /api/login real.clinician/docturn` → 200; `/api/user` shows a normal session with no flag. A skeptic reproduced the same through the real client code on both a synthetic and a real-PHI instance.

**Repro.** Log in as `ISPN`/`director`/`docturn`; add provider "Dr. Real Clinician" in the director dashboard; `curl -H 'Content-Type: application/json' -d '{"orgCode":"ISPN","username":"dr.real.clinician","password":"docturn"}' http://127.0.0.1:4100/api/login` → 200.

**Fix.** Server: in `server/routes/providers.ts` remove (or ignore) `password` in `createProviderSchema` (`:11`) and mint a server-side random one-time credential exactly as `server/routes/dev.ts:380` and `server/services/amion.ts:271` already do; return it once in the 201 body (or an invite token). Add `must_change_password BOOLEAN NOT NULL DEFAULT false` to `users` (`shared/schema.ts` + `SCHEMA_SQL` in `server/db.ts`), set it on every provisioned account, and add a gate middleware modelled on `mfaEnrollmentGate` that 403s everything except `/api/user`, `/api/logout` and `/api/account/password` until cleared. Independently reject the demo password (`DEMO_PASSWORD`/`"docturn"`) for any non-seed account creation and in `/api/account/password` on all instances, not only when `!isSyntheticDataMode()`. Client: delete `password: "docturn"` at `webapp/api-bridge.js:1614` and `:1652`; show the returned one-time credential or invite link in the "Provider added" / "Imported N provider(s)" toast or a copyable dialog (`DirectorDashboard.jsx`, `ScheduleSync.jsx`). Tests: in `tests/security-critical.test.ts`, a director- and er_director-created user returns 401 for login with `docturn` and 403 on `/api/patients` until the password is changed (mirror `tests/amion.test.ts:174-177`). Note the gap in `docs/AWS_DEPLOYMENT_RUNBOOK.md` §15 until fixed.

**Verification.** 2 skeptics, 2 of 2 confirmed at high confidence, both rated launch-blocker; one reproduced through the raw API and the real client code in both synthetic and real-PHI configurations.

### LB-3 — MFA: enrolled users see "Off / Set up"; one click silently replaces the live authenticator; no disable, regenerate or admin reset

**What happens.** `/api/user` omits `twoFactorEnabled`, so Account Settings shows "Off — recommended…" and a "Set up" button to every enrolled user. Clicking it calls `POST /api/mfa/enroll`, which — with no password or current-code check — deletes the active credential and inserts an unactivated one. From that moment the user's real authenticator stops working (only backup codes still do). A hijacked or unattended session can swap the second factor to an attacker's device; an honest user who opens "Set up" and backs out is locked out of TOTP. There is no route to disable MFA, regenerate backup codes, or for a director/developer to reset a locked-out user.

**Evidence.** `server/routes/mfa.ts:18-23` (`POST /api/mfa/enroll`, no credential prompt); `server/storage.ts:1573-1580` (`upsertMfaCredential` deletes the row and inserts `activated: false`); `shared/schema.ts:764` (`toSafeUser` omits `twoFactorEnabled`) → `webapp/AccountSettings.jsx:177-178` renders the "Off" state; MFA rows are only ever cleared in `deleteUser`/purge (`storage.ts:1511, 1559`). Observed: on an active MFA-completed director session, `POST /api/mfa/enroll {}` → 200 with a new secret; fresh login → 202; `complete-login` with the ORIGINAL authenticator's TOTP → `401 invalid_code`; a backup code → 200. A skeptic drove the real UI and confirmed the "Off / Set up" row and the setup modal for an enrolled user.

**Repro.** Log in as an MFA-enabled user and complete the second factor; `curl -b jar -X POST -H 'Content-Type: application/json' -d '{}' http://127.0.0.1:4103/api/mfa/enroll` → 200. New login → 202; `POST /api/2fa/complete-login` with a code from the ORIGINAL secret → 401; with a backup code → 200.

**Fix.** Three coupled changes: (1) `shared/schema.ts:764` include `twoFactorEnabled` in `toSafeUser` (or add it to `GET /api/user` at `server/auth.ts:369`) so `AccountSettings.jsx:177-178` shows "On". (2) `server/routes/mfa.ts:18-23`: if the user has `twoFactorEnabled`, require `{currentPassword, code}` and verify both (scrypt compare + TOTP against the ACTIVE credential or a backup code) before anything else; stop destroying the live credential — store the new secret as pending (`pending_secret` column or a pending row) and swap it in only inside `/api/mfa/verify`; `completeSecondFactor` (`server/services/mfa.ts:90-91`) keeps validating the old secret until the swap; audit as `mfa.reenroll` at `riskLevel: high`. (3) Add `POST /api/mfa/disable` and `POST /api/mfa/backup-codes/regenerate` (requireAuth + currentPassword + TOTP/backup, audited) and a director/developer reset route that clears `mfa_credentials` + `mfa_backup_codes` and sets `twoFactorEnabled=false`, audited. Test in `tests/mfa.test.ts`: enrol + verify, call enrol again, assert the ORIGINAL TOTP still completes login until the new secret is verified, and that enrol without credentials returns 401 for an enrolled user.

**Verification.** 2 skeptics, 2 of 2 confirmed at high confidence. The auth probe originally filed this as should-fix; both skeptics independently rated it launch-blocker, and the second extended the reproduction to the real Settings UI.

### LB-4 — Patient purge hangs on a foreign key, deletes assignments/consults without audit, and stalls hourly auto-clean for every later tenant

**What happens.** As soon as any patient has a patient-linked thread, `POST /api/maintenance/purge` never responds (the director's button spins forever) and the server logs an unhandled FK violation. Because the purge is not transactional, the patient's assignments and consults are already gone while the patient row remains, with no audit row. `runAutoClean` calls the same function inside a loop-wide try/catch, so one org's failure aborts auto-clean for every later org and the failing org is never cleaned.

**Evidence.** `server/storage.ts:518-551` `purgeOldPatients` deletes `assignments`, `patient_consults` and `patients` but never touches `conversations.patient_id` (`shared/schema.ts:180`); `server/services/expiry.ts:33-48` `runAutoClean`; route `server/routes/patients.ts:60-81`. Observed: director `POST /api/maintenance/purge {olderThanHours:0}` → `curl -m 10` HTTP 000 (also at 30 s); server log `[unhandledRejection] error: update or delete on table "patients" violates foreign key constraint "conversations_patient_id_fkey" on table "conversations"`. Control without a patient thread: `{"removed":1}` 200 in 72 ms. With `ops.retention` off → `404 module_disabled` (the gate works).

**Repro.** Login `er.doc` + `director` (ISPN). er.doc `POST /api/patients {initials:'QZ',roomNumber:'12B',issueSummary:'x'}` → id P; er.doc `POST /api/messaging/patient-thread {patientId:P}` → 201; director `POST /api/maintenance/purge {olderThanHours:0}` → never completes; FK error in the log.

**Fix.** (1) `server/storage.ts` `purgeOldPatients`: run inside `this.db.transaction` and, before deleting patients, either `UPDATE conversations SET patient_id = NULL WHERE organization_id = orgId AND patient_id IN (ids)` (keeps history) or delete the patient threads with messages, `message_attachments` (+ encrypted files), delivery rows and the conversation in FK order. (2) `server/services/expiry.ts` `runAutoClean`: move the try/catch inside the per-org loop and append an audit row (`autoclean.sweep_failed`, `riskLevel: high`, error text only) as `retention.ts:21-53` does. (3) Express 4.22.2 does not forward async rejections to the error middleware at `server/app.ts:239` — add an `asyncHandler` wrapper (or `express-async-errors`) so this class returns a 500 instead of hanging; give `rawApi()` in `webapp/api-bridge.js` a fetch timeout. (4) Tests: patient → patient-thread → purge expects `200 {removed:1}`, patient/assignment/consult gone, audit `maintenance.purge_patients` present, conversation unlinked or removed; `runAutoClean` with a failing first org still purges a later org and records the failure. (5) Audit `deleteOrganization` and every other patient cascade for the same omission (`docs/PERFECTSERVE_PARITY_BLUEPRINT.md:512` already flags cascade gaps).

**Verification.** 2 skeptics, 2 of 2 confirmed at high confidence, both rated launch-blocker; the second reproduced it twice on fresh instances.

### LB-5 — No way to terminate a clinician's access (critic finding; single-agent evidence, not skeptic-verified)

**What happens.** A director's "Remove" deletes only the rotation profile; the account keeps working and can log in again. The People screen's trash button calls a developer-only route, so a director always gets `403` and the toast "Delete failed." The developer's delete refuses any user who has ever done anything (`409 user_has_activity`). There is no `active`/`disabled` column, no deactivate route and no admin password reset. HIPAA §164.308(a)(3)(ii)(C) (termination procedures) cannot be met from the application.

**Evidence.** As director: `POST /api/director/hospitalists` → user 30 `leaver` (hospitalist 19) and user 31 `erleaver` (er_doctor); `leaver` logs in → 200 (session A); director `DELETE /api/physicians/19` → 204 (what `webapp/api-bridge.js:1625` `removeProvider` calls). Afterwards session A: `GET /api/user` → 200 `leaver`, `GET /api/patients` → 200, `GET /api/messaging/conversations` → 200, `GET /api/physicians/directory` → 200; a fresh login as `leaver` → 200; `/api/users` still lists both. Director has no route for er_doctors: `DELETE /api/users/31` → 404 (SPA fallback), `DELETE /api/dev/users/31` → 403. `webapp/People.jsx:167` `a.removeUser` → `DELETE /api/dev/users/:id` (`api-bridge.js:1728`), `requireRole('developer')`. As developer: `DELETE /api/dev/users/30` → `409 user_has_activity` (leaver has only ever logged in); `DELETE /api/dev/users/8` (liu, received one message) → 409; only never-used user 31 → 204. `server/storage.ts:1554-1563` `deleteUser` does not touch `audit_logs`/`messages`, so the FK makes any active user undeletable. `shared/schema.ts` has no active/disabled column; dev impersonating `leaver` then `PATCH /api/account/password` without the current password → `403 wrong_password`. Final check: `leaver` login → 200 after every attempt.

**Repro.** (1) Login director ISPN; `POST /api/director/hospitalists {username:'leaver',password:'Leaver12345',displayName:'x',role:'hospitalist'}` → note hospitalist id H and user id U. (2) `POST /api/login leaver` → 200. (3) Director `DELETE /api/physicians/H` → 204. (4) `GET /api/user` and `/api/patients` with leaver's cookie → 200; `POST /api/login leaver` again → 200. ## 7. Refuted

Every finding in the verification record was confirmed; the skeptics overturned framings and root causes, not defects.

- **"The critical proxy-addr CVE defeats per-IP login rate limiting"** (baseline summary) — refuted as a mechanism: `server/app.ts:43` sets `trust proxy` to the numeric hop count 1, so Express never calls `proxyaddr.compile()` and the vulnerable IPv4-mapped-IPv6 subnet matcher is unreachable. The advisory remains dependency hygiene (SF-1). The limiter *is* bypassable via `X-Forwarded-For` wherever the Node port is reachable directly, but for an unrelated reason (SF-7).
- **"Interop step 5 fails because the phone UI has no Acknowledge control"** — refuted: the `[data-broadcast-ack]` button renders within ~320 ms and the click succeeds 5/5 when retried; a clean-server re-run passed 18/18. The failure is the toast overlap window plus a 3,000 ms budget the click meets at 2,943–3,005 ms (SF-16, SF-18).
- **"ui-smoke `LOGIN as er_doctor` is a login/server flake"** — refuted: no `/api/login` request failed or returned 4xx in any run and the server logged no errors; the harness clicks the icon-only Sign out button and races itself (SF-19). The earlier-reported ui-smoke hang after "live API bridge active" did not recur in either 9-minute run.
- **Auth probe's sibling comparison "`POST /api/assignments/<HOSP id>/accept` → 404"** — a method mismatch: the route is `PATCH` (`server/routes/assignments.ts:148`) and checks ownership at `:155-156`. The consults finding (SF-5) stands on the other two siblings.
- **Auth probe's "MFA re-enrolment" as should-fix** — not refuted but re-rated: both skeptics independently raised it to launch-blocker (LB-3).

## 9. Method & limits

**How this was verified.** Nine independent probe agents (baseline, auth, messaging, routing, platform, PWA install, PWA layout, PWA flows, PWA realtime) each ran the application from git HEAD `81bb06e` on their own isolated servers — separate ports and fresh PGlite data directories, with variants for `NODE_ENV=production`, `SYNTHETIC_DATA=false` + `PLATFORM_ADMIN_PASSWORD`, `RATE_LIMIT` on, `ATTACHMENT_STORE=fs-encrypted`, `TRUST_PROXY=0` and the compiled `npm start` build. Predictions were written before calls where an algorithm was under test (routing). Phone behaviour was exercised in real headless Chromium (build 1194, via playwright-core) with iPhone emulation: iOS 17 user agent, `isMobile`/`hasTouch`, 390×844 @3× plus 375×667 @2× and 430×932 @3× in verification, capturing the actual HTTP bodies the page sent. Every finding was then handed to one or two independent skeptic agents who re-derived it from the code and re-ran it on their own servers; verdicts were decided by majority and recorded with confidence and a severity rating, and skeptics were free to overturn the finding, its mechanism or its proposed fix (Section 7). A completeness critic reviewed the whole digest, listed what no probe had exercised, and closed those gaps with direct probes, including on a production-like instance (Section 8). The repository was left unmodified after every run (`git status --short` empty) and all verification servers were shut down.

**Honest limits.**

- **No WebKit.** Nothing ran on a real iPhone, Safari or WebKit. Standalone-mode cookie persistence, the Add-to-Home-Screen flow, push permission and delivery through Apple's push service, Safari's toast/safe-area rendering, keyboard auto-capitalisation, focus zoom, `<audio>` behaviour without Range support, MediaRecorder output, and whether iOS suspends the 60 s poll in the background are all inferred from DOM attributes and server behaviour, not observed (Section 6).
- **No real Epic, Amion or Twilio.** Amion and Epic syncs ran against a local fixture server; SMS reached only the console stub (no `TWILIO_*` credentials exist); push payload shapes were verified from code and unit tests, not against a live push service.
- **Synthetic data only.** All tenants, users, patients and messages were the seed fixtures or created during the run; real-PHI mode was exercised for its provisioning and gating behaviour, not with real records.
- **PGlite only.** The in-process database was the only store; the Postgres driver path, `connect-pg-simple`, RDS encryption-at-rest and multi-instance behaviour were not exercised.
- **Timing is indicative.** Builds, test suites and latency figures ran on a shared 4-core sandbox alongside other agents.
- **Advisories are a snapshot.** `npm audit` reflects registry data at run time; the proxy-addr and drizzle issues were confirmed as advisories plus code paths, not exploited.
- **Flakes.** The ui-smoke `er_doctor` login failure appeared in 1 of 2 unmodified full runs; the previously reported harness hang did not recur, so its stall point was not located.
- **Input truncation to this report.** The per-check list for routing, all results for the platform and four PWA probes, and the skeptic records after LB-4 (including LB-7 and the messaging/routing should-fix items in 4.6) were cut from the data this report was written from. Those items are labelled accordingly rather than inferred.
